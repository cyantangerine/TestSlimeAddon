## SmartContainer 堆叠上限系数 + transfer 合并堆叠，新增 SmartBackpack

- 背景：`SmartCooler.loadFromContainer` 原写死「一格一瓶」（玻璃瓶/药水 maxStackSize=1）。抽离 `SmartContainer` 父类后要支持通用物品，故按「物品自身 maxStackSize × 容器系数」计算单格上限。
- 用户确认的两个决策：① 本次同时新建并注册 `SmartBackpack`；② 单格上限**不封顶**（64 堆叠物品在系数 4 下 = 256/格，玻璃瓶 = 4/格）。背包 GUI 内原版点击仍按 vanilla maxStackSize 合并，插件只在批量装载 / 快捷存入时执行自定义上限。
- 改动：
  - `SmartContainer.java`：新增 `protected abstract int getStackMultiplier()` 与 `getStackLimit(ItemStack)`（用 `ItemStack#getMaxStackSize()` 而非 `Material` 的，1.21 的 max_stack_size 组件自动生效；long 防溢出）；`getStackMultiplier` SmartCooler=1 / SmartBackpack=4。
  - `transfer` 重写：删掉 `freeSlots`/`free` 与「一格一瓶」TODO；新增 `findDestinations`（先同类部分堆叠、后空槽，返回 {slot, room}）与 `placeInto`（按 room 写入，可写 amount>64 的堆叠）。每个源槽位按 `min(源数量, 总 room)` 精确扣减容器库存，能只搬走一叠的一部分；某类物品放不下时继续试后面的槽位（不再提前 return）。`LoadResult.total` 现在是个数而非格数。
  - `putIn` 同样改为合并堆叠 + 放不下的部分 `giveBack` 退还；`CONTAINER_FULL` 的 `%s` 补上 `String.format`(新增 `containerName`)。
  - 泛化：`isJuice`→`isAllowedItem`、`juiceName`→`itemName`、默认消息改为「非潜影盒、非背包」；`SmartCooler` 同步调用点。
  - 新 `SmartBackpack.java`：`CAPACITY=54`、`STACK_MULTIPLIER=4`，默认占位 ICE、容量条占位 PAPER（maxStack 64，1.19.2/1.21 bundle 权重 = 数量/64，进度条才准确）；`isItemAllowed` 沿用 `SlimefunBackpack` 默认（拒绝潜影盒/背包），`preRegister` 里自行 `registerEvents`。
  - `CyanTestAddon.java` 注册 `SMART_BACKPACK`，配方中心用原版 `CHEST`（不放任何 `SlimefunBackpack`，避免走 `AbstractCraftingTable#upgradeBackpack` 继承旧背包语义）。
- 两个 SmartContainer 子类各注册一份 Listener：`isOurContainer` 是排他的，一次点击只有一种容器会被认领，另一实例自然落到「无关背包」分支返回；**不要**加「非本实例 GUI 就整段 return」的守卫，那会破坏「GUI 内右击另一个容器切换」的既有行为。
- 验证：离线 Maven + JDK 21 `clean package -DskipTests` BUILD SUCCESS（9 源文件），jar 内含 `SmartBackpack.class`。**未部署、未进游戏实测**（需用户自行 `deploy.ps1` + 实测批量装载/创造模式）。
- 顺带发现（未改）：`SmartCooler` 的容量条占位物是 `GLASS_BOTTLE`（maxStackSize=1），但重构后的 `createFiller` 已不再反射调 `ItemMeta#setMaxStackSize`，1.19.2/1.21 的 bundle 权重会变成 数量/1，条可能一直画满。SmartBackpack 已用 PAPER 规避。→ **本日稍后已修复，见下一段。**

## 修复容量条一直画满（上条的既有问题）

- 根因：重构前 `VisableCooler.createFiller` 有两条分支 —— 1.20.5+ 反射调 `ItemMeta#setMaxStackSize(CAPACITY)` 并把数量设为 `used`；1.19.2 无此 API 才退回 `legacyAmount = ceil(64*used/CAPACITY)` 的数量映射。抽父类时只搬了后者，于是新版上 `GLASS_BOTTLE`（原版上限 1）权重恒 ≥ 满格。
- 运行时证据（反编译本机 `MCServer/folia/versions/26.3/folia-26.3.jar`）：`BundleContents.computeContentWeight` = `Σ count / ItemInstance.getMaxStackSize()`，`getWeight` = `Fraction(1, maxStackSize)`，满格为 `Fraction.ONE`。`getMaxStackSize()` 读的正是 `max_stack_size` 组件，所以反射设置有效；`paper-api 26.3` 有 `setMaxStackSize(Integer)`，`spigot-api 1.19.2` 没有 → 两条分支都会按版本正确命中。
- 修复（`SmartContainer.java`）：新增 `import java.lang.reflect.Method`、`SET_MAX_STACK_SIZE = findSetMaxStackSize()`（缓存反射 Method，找不到即 1.19.2）。重写 `createFiller`：新版分支用 `getPlaceholder()` 造 `amount=used` 的占位物，反射写 `maxStackSize=getCapacity()`，并在**同一个 meta** 上写 PDC 标记后一次 `setItemMeta`（避免两次 setItemMeta 互相覆盖）；反射失败/mate 为 null 时退回 legacy 映射。`isLoosePlaceholder` 数量上界从 `getCapacity()` 放宽到 `max(getCapacity(), 64)`，覆盖 legacy 映射 1..64 的数量域。
- 保留 `GLASS_BOTTLE` 不换材质：换 64 堆叠材质会与未初始化的 ICE 占位物在创造模式宽松识别里混淆；反射分支让材质不再影响权重。同步更新 `SmartCooler` / `SmartBackpack` 的注释。
- 验证：离线 Maven `clean package -DskipTests` BUILD SUCCESS（9 源文件）。**仍未部署、未进游戏实测**，进度条效果需在 Folia 26.3 上打开冰柜 GUI 观察。

## 实测反馈：>64 堆叠会消失 → 堆叠上限改为封顶 64（推翻上午的「不封顶」决策）

- 用户实测：背包内从来没有 >64 的堆叠；从容器装载后写成 >64 的物品整叠消失。上午选的「不封顶」方案不可用。
- 反编译本机 Folia 26.3 取证：
  - `DataComponents` 静态初始化里 `MAX_STACK_SIZE` 默认值是 `bipush 64`；`lambda$static$1`（对应注册 `max_stack_size` 的 InvokeDynamic #1）用 `ExtraCodecs.intRange(1, 99)` → 组件合法范围只有 **1..99**，256 连声明都不可能。
  - `CraftItemStack#setAmount(int)` 只是 `handle.setCount(int)`，NMS `setCount` 只是 `putfield count`，**都不校验**。所以 256 能写进 Bukkit Inventory，但属于客户端不认的非法状态；GUI 同步 / 点击拆分 / Slimefun 背包存档往返后会整叠丢失。
  - 1.19.2 则由材质写死 1/16/64，同样没有 >64。
- 修复：`SmartContainer` 新增 `public static final int VANILLA_MAX_STACK_SIZE = 64`；`getStackLimit` 由 `min(limit, Integer.MAX_VALUE)` 改为 `min(limit, 64)`。系数仍对小堆叠物品生效：玻璃瓶/药水 1→4、末影珍珠/雪球 16→64、64 堆叠物品维持 64。同步改 `getStackMultiplier` / `transfer` 的 Javadoc、`SmartBackpack` 类注释与 lore（「最高 64」）。
- `findDestinations` 对已残留的非法堆叠（amount>64）算出的 room 为负，本来就会跳过，不会继续往里塞，无需额外清理。
- 验证：离线 Maven `clean package -DskipTests` BUILD SUCCESS（9 源文件）。**未重新部署**，用户需自行 `deploy.ps1` 后复测装载。
- 教训：Bukkit API 允许 ≠ 原版/客户端支持。涉及 amount 的自定义上限必须以 `max_stack_size`（默认 64）为天花板，不能只看 API 是否能写。

## 确认：createInventory 不能超过 54，客户端也画不出第 7 行

- 结论：**服务端 + 客户端两层都是硬限制**，不是显示 bug，纯插件无解。`SmartBackpack.CAPACITY=54` 已是上限。
- 服务端：Bukkit `Server#createInventory` 的 Javadoc 只写「9 的倍数」，但 `CraftServer.createInventory` 实际是 `Validate.isTrue(9 <= size && size <= 54 && size % 9 == 0, "Size for custom inventory must be a multiple of 9 between 9 and 54 slots (got " + size + ")")`；1.14 / 1.19.3 / 26.x 都在，传 63 直接抛 IllegalArgumentException。`Server.java` 的 @throws 也因此具有误导性。
- `lib/Slimefun-DEV-SNAPSHOT.jar` 的 `PlayerBackpack.class` 常量池含 `Bukkit`/`createInventory`/`size` → Slimefun 背包走同一 API，改 CAPACITY 为 63 会在建包时炸。`SmartContainer.isBackpackInventory` 里的 `getSize() > 54` 兜底是对的，保持即可。
- 客户端：1.14+ 的 Open Screen 包只有 windowId / menu 注册表类型 / title，**没有 slot count**；`minecraft:menu` 通用容器只有 `generic_9x1`..`generic_9x6`，客户端按 rows 建 `9*rows+36` 槽。伪造 menu id 会解码失败；发 `generic_9x6` + 54..62 槽数据客户端不认，既不可见也点不到。资源包只改贴图，只有客户端 Mod 能注册新 menu type。
- 历史：1.13 及以前协议带 slotCount，老版本曾能开 >54（界面绘制异常但多余槽位可存取），1.14 改注册表后封死。
- 扩容方向：分页（多个 54 格视图 + 翻页，后端自管页数据）或提高单格堆叠（本项目已封顶 64）。不存在「单个 63 格 GUI」的插件级方案。

## 新增：智能存储交互接口 + 智能存储连接器（分页式存储终端）

新增 4 个源文件 + 改 `CyanTestAddon.java` 注册，均已编译通过（13 源文件），**未部署、未进游戏实测**。

- `model/StorageNetwork.java`：`BlockKey`（world UID + xyz，无 yaw/pitch）、`ContainerRef` / `ConnectorRef` / `Network`。从接口 6 邻格的连接器作 BFS 根（距离 1），只沿连接器泛洪（箱子是叶子，不经箱子合并两个网络），距离 = 经过的连接器个数最短路；容器数封顶 32，连接器封顶 512。容器只认 CHEST / TRAPPED_CHEST / BARREL，且 `BlockStorage.check(block) != null` 一律跳过。同一容器挨着多个连接器取 min 距离。
  - **大箱子关键坑**：Folia 的 `block.getState()` 是快照，快照 `CraftChest#getInventory()` 因 `isPlaced()==false` 只返回那一半的 27 格，拿不到合并的 54 格。故反射调 Paper 专有 `Block#getState(false)`（`Block` 接口在 folia-api 26.3 已声明；spigot-api 1.19.2 没有，退回 `getState()`）。去重键用 `Inventory#getLocation()`：单箱子是方块坐标，大箱子是两半中点，按「×2 取整」编码避免与单箱子撞键。

## 追加：lombok scope + 「界面打开时被漏斗/货运改动」的并发审查

- `pom.xml` lombok 已改 `<scope>provided</scope>`；产物 jar 从 ~2.1 MB 降到 **140 KB**，`unzip -l | grep lombok` = 0。shade 里 `CHANGE-THE-GROUP.CHANGE-THE-PLUGIN-NAME.lib.folialib`  relocation 占位符仍未动（功能无影响，只是包名难看）。
- **查证到的关键事实（javap Slimefun DEV jar）**：
  - `CargoNet#classifyLocation` 只认 5 个 `CARGO_*` ID，所以接口方块不是货运节点；**但** `tags/cargo_supported_storage_blocks.json` 里含 `minecraft:dispenser`。`CargoUtils#insert/withdraw` 对 `hasInventory(block)==true` 的方块直接走 `getState(false)` → `InventoryHolder#getInventory()` → `Inventory#addItem/setItem`，**不经过 `InventoryMoveItemEvent`**。也就是说原实现只用 `InventoryMoveItemEvent` 拦漏斗，货运照样能往接口方块自己的 9 格发射器库存里塞/抽物品 → 这是「不响应货运系统」的真实漏洞。
  - 可拦并且来得及拦：fork 里 `slimefuncomplib` 提供 `CargoOperationEvent`（`CargoInsertEvent`/`CargoWithdrawEvent` 的父类，`CancellableEvent extends org.bukkit.event.Event`，自带静态 `getHandlerList`）。字节码确认事件在**扣物品/写库存之前** `callEvent` 并检查 `isCancelled`。两个子类都不覆写 `getHandlers()`，所以**注册父类一次即可同时拦插入和取出**。
  - `CargoUtils#hasInventory` 用方块材质标签判定，不排除 Slimefun 方块；连接箱（CHEST/BARREL）同样可被货运操作。
- **结论：默认不禁用漏斗/货运对「已连接箱子」的搬运**。理由：规格里的「不响应货运系统」说的是接口方块本身（已修）；冻结普通箱子会让自动化在有人看界面时莫名停摆；且玩家直接开箱、其它插件直写库存都拦不住，「禁用」给不了严格一致性。改为让界面变成实时视图。
- 落地改动：
  - `SmartStorageInterface`：新增 `CargoGuard` 独立内部类（用 FQN 参数，外层类常量池**不含** `CargoOperationEvent`，换回无此事件的 Slimefun 版本只是少一道拦截、不会 NoClassDefFoundError 拖垮整个物品）。接口方块本身永久 `setCancelled(true)`，与配置无关。
  - `options.smart-storage-lock-external-transfers`（config.yml，默认 false）：为 true 时，界面打开期间额外取消 `InventoryMoveItemEvent` 与 `CargoOperationEvent` 中指向已连接容器的搬运。容器用 `StorageNetwork.inventoryKey(Inventory)`（`Inventory#getLocation()` 的 ×2 坐标键，与 `ContainerRef.key` 同规则）比对，不用对象相等。
  - 实时刷新：`runAtEntityTimer` 每 20 tick 用 `StorageSnapshot.fingerprint`（容器 key + 每组的 template hash/total/perContainer）比对，**有变化才重绘**，避免每秒 clear() 54 格造成客户端闪烁；每 100 tick 完整 `refreshNetwork`。每次 `InventoryClickEvent` 前先 `rescanIfChanged`，保证 `labelSlots` 对应玩家当下看到的数据。关界面/退出/重开时 `WrappedTask.cancel()`。
  - `take()` 的 `wanted` 从**快照** `min(maxStack,total)` 改成直接 `maxStack`，由 `StorageNetwork.take` 扫实时库存自然封顶（不足一组取全部），避免漏斗刚补货时少取。
  - 真正会丢物品的路径：界面开着时箱子被拆，缓存 `Inventory` 指向已清空且脱离世界的方块实体，「存入」会写进虚空。新增 `BlockBreakEvent`/`BlockPlaceEvent` → `StorageNetwork.withoutContainer(Network, BlockKey)`（大箱子拆任一半都能命中，含 `Inventory#getLocation()` 中点）当场从网络剔除，再排一次重发现；接口方块自己被拆则关掉该玩家 GUI。

- `pom.xml` shade relocation 的模板占位符 `CHANGE-THE-GROUP.CHANGE-THE-PLUGIN-NAME.lib.folialib` 改为 `me.cyantangerine.slimefunaddon.lib.folialib`。已用 `javap -v` 确认 jar 内 FoliaLib 类路径、以及 `CyanTestAddon`/`ResourceLib` 常量池里的 `com/tcoded/folialib` 引用全部同步改写，无残留。产物 138,971 B。

## 智能存储 GUI 第二轮改造（7 项需求）
- **潜行放置**：`SlimefunItemInteractListener#openInventory` 字节码里 Slimefun 自己就有 `isSneaking() && item != AIR → return` 的约定；`PlayerRightClickEvent` 的 itemResult/blockResult 初值直接取自 `PlayerInteractEvent.useItemInHand/useInteractedBlock`，不 cancel 就不会被改成 DENY。所以只在两个物品的 `BlockUseHandler` 开头加 `SmartStorageInterface.isSneakPlacing(event)` 早退即可（原实现无条件 cancel + DENY 导致放不上方块）。
- **残留标记 bug 根因**：服务端取消点击后会单独重发「被点击槽位」的旧内容，事件内 `inventory.clear()` 重绘盖不掉这个后置包 → 点纸取空最后一组时物品格没了、纸还在；重新开窗或再点别处（又整屏 clear）才消失。修复：点击结束后 `runAtEntityLater(player, ..., 1L)` 强制 `StorageSnapshot.of` + `render` + `updateInventory()`，只对 top 54 格点击排（背包点击不排，免得干扰整理背包）。

## 中文名表乱码修复（23:53）

- 现象：用户反馈 `src/main/resources/lang/zh_cn_items.properties` 乱码。字节检查确认文件实际是 **GBK/GB18030**（首行 `BD F0 BA CF BB B6...` = 金合欢木按钮），而 `VanillaItemName` 用 `InputStreamReader(UTF-8)` 读 → 编辑器和运行时都会乱码；上一版 jar 里那份也是 GBK 字节。
